Domain Concept:
Inventory reservation system designed to demonstrate idempotency + concurrency correctness.

Core Entities (bounded; keep minimal):
1) InventoryItem
   - id (UUID)
   - sku (string, unique)
   - total_quantity (int)
   - reserved_quantity (int)
   - version (int optional; include if using optimistic lock patterns)
   - created_at / updated_at

2) Reservation
   - id (UUID)
   - sku (string)
   - quantity (int)
   - status (enum)
   - idempotency_key (string, unique)
   - created_at / updated_at

---

Reservation States:
- active
- confirmed (terminal)
- canceled (terminal)
(Optional: expired terminal only if explicitly added; avoid unless required.)

State Transitions:
active → confirmed
active → canceled
Illegal transitions:
confirmed → anything
canceled → anything
(active cannot be reconfirmed as new state; confirm is idempotent no-op)

Illegal transitions raise explicit domain errors and are tested.

---

Invariants (must always hold):
- reserved_quantity <= total_quantity (never oversell)
- Reservation create is idempotent by idempotency_key
- Confirm/cancel operations are idempotent (safe retries)
- Inventory + reservation updates are atomic (no half-state)

---

Concurrency / Correctness Model (explicit):
Primary reservation approach = ATOMIC CONDITIONAL UPDATE on InventoryItem:

Reserve attempt:
- Update InventoryItem set reserved_quantity = reserved_quantity + qty
- Condition: reserved_quantity + qty <= total_quantity
- If rowcount == 0 → insufficient inventory / contention → 409

Reservation create must occur within explicit transaction boundaries:
with session.begin():
- create Reservation row (idempotency enforced by unique constraint)
- apply inventory reservation update atomically (or vice versa, but atomicity guaranteed)
- on any error → rollback, no partial effects

Idempotency:
- POST /reservations requires idempotency_key (header or field)
- Unique constraint on idempotency_key enforces dedupe
- Duplicate key returns existing reservation deterministically (policy documented) OR 409 (policy documented)
- Confirm/cancel repeated calls return stable outcome (no double decrement)

---

API Endpoints (tight; enterprise-safe):
POST  /reservations                 → create reservation (idempotent)
GET   /reservations/{id}            → retrieve reservation
POST  /reservations/{id}/confirm    → confirm (idempotent)
POST  /reservations/{id}/cancel     → cancel (idempotent)
GET   /inventory/{sku}              → view inventory

Error envelope required everywhere:
{
  "error": {
    "code": "machine_identifier",
    "message": "human readable"
  }
}
No raw exceptions returned.

---

Failure Matrix (table-only; must be explicit and tested):
- Invalid input → 422
- SKU not found → 404
- Insufficient inventory / contention → 409
- Duplicate idempotency_key → deterministic behavior (return existing or 409) documented + tested
- Illegal transition (confirm canceled, cancel confirmed) → deterministic error (400 or 409) documented + tested
- DB unavailable → 503
- Timeout → 504
- Partial transaction risk → deterministic rollback (no half-reservation, no oversell)
- Concurrency edge cases must map to deterministic errors

Testing Requirements (the differentiator):
1) No-oversell concurrency test:
   - total_quantity=10
   - launch N concurrent reservation requests totaling >10
   - assert final reserved_quantity == 10
   - losers receive deterministic 409
2) Idempotent create:
   - same idempotency_key repeated returns stable reservation outcome
   - no double reservation applied
3) Idempotent confirm/cancel:
   - confirm twice returns stable result (no double effects)
   - cancel after confirm → illegal transition error
4) Atomicity test:
   - simulate failure mid-operation; assert rollback leaves consistent state
5) Migration test (upgrade/downgrade)
Coverage target 80–85%, CI enforced.
